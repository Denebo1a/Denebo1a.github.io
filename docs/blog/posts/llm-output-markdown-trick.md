## 提出问题
在LLM时代，**Markdown**（以下简称md）已经从单纯的简单易用的标记语言变成了人与大模型交流的一种标准格式。大模型很自然地使用 md 输出回答，很舒服，某种意义上的也很有“AI味儿”。

在 99% 的日常使用场景下，用户期望看到的都是直接可读的富文本。因此，在所有主流大模型的产品设计中，强制的富文本渲染都是绝对优先的，聊天界面的前端页面都会全局挂载一个强大的 Markdown 解析器。

设想一个边缘场景，假如我们不想看到美观易读的富文本，而是希望拿到纯净的 md 源码呢？

——比如说，我们想把大模型的回复直接粘贴到自己的md文档中，直接复制渲染好的富文本显然行不通，所有由 md 标记的样式与结构都会丢失，我们只会得到一段平铺式的纯文字，有时换行还是乱七八糟的。

这个问题虽然超级让人抓狂，不过正如上面所说的，其成因十分好理解，所以解决起来还是很有头绪的，探索一些解决方案甚至可以说很有趣。以下列出几种可能可行的解决方案~

## 解决方案
核心思想很简单，我们的敌人只有一个，那就是 Markdown 渲染器，只要 md 源码能逃过它的魔爪，一切就水到渠成了。

### 提示词工程
这个我想大家肯定都试过ww，很直接的想法是，在prompt中追加一句，表明自己的特殊需求。

- **“输出 Markdown 源码” / “不要给出渲染后的版本”**：不假思索地这么写，然后被自己气笑，模型虽然理解了需求，但是前端的解析器管你有的没的，文本流中的 md 语法结构不被狠狠渲染一番是逃不出去的（悲）。
- **“将 Markdown 源码包裹在代码块中”**：哦哦这个不错耶，代码块是一个很安全的沙箱，里面嵌套的 md 源码只会被交给 Shiki 等代码高亮组件处理（相当于没处理），不会被解析渲染，可以得到很好的保护。
- **“将输出的 Markdown 源码包裹在 {} 中”**：这也是个很棒的思路，当然也可以是其他的字符，只要能直接破坏 md 的根节点的标准结构，让解析器降级。
- **“将输出的 Markdown 源码转化为 Base64 编码后再输出”**：这是相当终极的解决方案了，是加密，我使用了简单的加密，解析器下辈子都识别不出来。但是输出 token 可能会有所增加。
- **“防止 Markdown 源码被自动渲染到当前对话的浏览器中”**：为了保险或许可以再加上这一句，让模型明白你的意图总是有益无害的。
